# 日本語コミットメッセージ

## 基本形式

コミットメッセージは、次の2段構成にする。

```text
<prefix>: <日本語の要約>

<日本語の詳細説明>
```

- `prefix` だけを英語の小文字で書く。
- Prefix以外の文章は日本語で書く。識別子、ライブラリ名、URL、Issue番号、エラーメッセージなど、意味上必要な固有表現は原文を許容する。
- 1行目と詳細説明の間には空行を1行だけ置く。
- 詳細説明は原則として付け、変更の理由、範囲、影響、検証のうち差分から読み取りにくいものを短く補足する。

## Prefixを選ぶ

リポジトリの `AGENTS.md`、`CONTRIBUTING`、commitlint設定、直近の履歴に明示的な規約があれば、それを優先する。規約がなければ次から選ぶ。

| Prefix | 用途 |
| --- | --- |
| `feat` | 利用者向けの機能を追加・変更する |
| `fix` | 利用者向けの不具合を修正する |
| `docs` | ドキュメントを更新する |
| `refactor` | 振る舞いを変えずに構造を改善する |
| `style` | フォーマットや見た目だけを変更する |
| `test` | テストを追加・修正する |
| `chore` | ツール、依存関係、設定など本番機能以外を保守する |

複数の変更が含まれる場合は、最も利用者に近い主目的をPrefixにする。ただし、独立した目的が混ざっているなら、メッセージで隠さずコミットを分ける。`Merge` や `Revert` などGitが生成する特殊なコミットは、この形式の対象外としてよい。

## 1行目を書く

- 変更内容を「何をどうするか」で短く表す。目安は20〜30文字程度とする。
- 過去形の「追加した」「修正した」ではなく、現在形・動作形の「追加する」「修正する」で書く。
- 末尾に句点を付けない。
- 変更が自明でない場合は、Issue番号をPrefixの直後に置く（例: `fix: #123 ログイン失敗時の表示を修正する`）。Issueがなければ無理に作らない。
- Emojiは既存規約で必須でない限り付けない。
- 「テストを書く」「修正する」のように内容が広すぎる表現を避け、対象と結果が分かる粒度にする。

## 詳細説明を書く

詳細説明は、差分を読めば分かる操作の列挙ではなく、未来の開発者が履歴から意図を追える説明にする。

- なぜ変更したかを書く。IssueやPull Requestに理由がある場合は、コミットには重複しない要点だけを書く。
- 何を変更したか、影響範囲、互換性や制約があれば補足する。
- 実際に実行したテストや確認だけを書く。未実行の検証結果を推測で書かない。
- 説明が一文で済む場合も、空行後に日本語の一文を置く。ユーザーがワンラインを明示した場合だけ本文を省略する。

## コミットを作る手順

1. 依頼がメッセージ案だけか、実際のコミット作成まで含むかを確認する。案だけならGitの状態を変更しない。
2. `git status` と差分を確認し、対象範囲、変更理由、検証状況を把握する。既存のステージ済み変更と未ステージ変更を混同しない。
3. プロジェクトの規約と直近のコミットを確認し、Prefixとメッセージを決める。
4. 独立した目的の変更を分離し、対象ファイルだけをステージする。ユーザーが作業中の無関係な変更を勝手に含めない。
5. 必要なテスト、静的検査、`git diff --cached --check` を実行する。検証に失敗した場合は、成功したような詳細説明にしない。
6. ユーザーがコミットを明示的に依頼している場合だけコミットを作成し、作成後にハッシュ、メッセージ、検証結果を報告する。

## 例

```text
feat: 投稿一覧にカーソルページネーションを追加する

投稿件数が増えたときの全件取得を避けるため、カーソルを使った一覧取得と次ページ用のレスポンスを追加する。
```

```text
fix: #42 投稿削除後に一覧へ残る不具合を修正する

削除成功後にキャッシュを無効化していなかったため、一覧取得時に削除済みの投稿が表示されていた。関連するサービスのテストを更新する。
```

```text
docs: APIの起動手順を更新する

現在のDocker Compose構成とヘルスチェックの確認方法に合わせて、READMEの手順とコマンド例を更新する。
```
