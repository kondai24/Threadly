# Threadly コメント基準の詳細

## 判定基準

| 基準     | 書く内容                                                       | 避ける内容                                             |
| -------- | -------------------------------------------------------------- | ------------------------------------------------------ |
| 情報量   | コードから復元しにくい意図、制約、影響、契約                   | `x = x + 1` に対する「xに1を足す」のような直訳         |
| 実行時点 | コメント地点で成立している状態、分岐の前提、処理後の重要な状態 | まだ実行していない処理を、既に成立した状態のように書く |
| 理由     | なぜ必要か、削除・変更すると何が壊れるか                       | 「重要」「注意」「理由は不明」だけの曖昧な警告         |
| 対象読者 | 初めて読む人と、将来の自分が判断できる具体性                   | 実装者の記憶に依存する略語や背景の省略                 |
| 維持性   | 安定した仕様・不変条件・境界を説明する                         | 変数名、行順、現在の一時的な実装を重複する             |

## 良いコメントと避けるコメント

### 分岐の時系列

避ける例は、分岐前に分岐後の状態を書いてしまうこと。

```go
// 返信を削除済みにする
if comment.ParentID == nil {
    deleteQuery = tx.Where("id = ? OR parent_id = ?", comment.ID, comment.ID)
}
```

この位置ではまだ親Commentか返信かが確定していないため、読み手はコメントと条件を往復する。必要なら分岐ごとの現在条件を分岐内に置く。

```go
if comment.ParentID == nil {
    // 親Commentの削除では、同じ親に属する直接の返信も論理削除する。
    deleteQuery = tx.Where("id = ? OR parent_id = ?", comment.ID, comment.ID)
} else {
    // 返信の削除では、親Commentと兄弟の返信を残して自身だけを論理削除する。
    deleteQuery = tx.Where("id = ?", comment.ID)
}
```

`if` の前に置く場合は、分岐前の不変条件を書く。

```go
// Commentの削除範囲とCommentLikeの掃除を同じトランザクションで確定する。
err := r.DB.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
    // ...
})
```

### Threadlyで必ず理由を残す場面

- **認証・認可**：認証情報からUser IDを取り、リクエストのUser IDを信用しない理由を書く。所有者でないResourceをNotFoundとして返して存在を隠す場合も、セキュリティ上の理由を書く。
- **エラー境界**：Repositoryの `gorm.ErrRecordNotFound` をアプリケーションエラーへ変換する地点、または複数の認証失敗を同じ応答へまとめる理由を書く。ORMエラーをそのままHTTPへ出さない。
- **データ整合性**：Post・Comment・Likeの削除、関連行の掃除、複数操作のTransaction、ロックが同じ整合性境界に属する理由を書く。
- **Comment契約**：`parentID = nil` がPost直下、非nilが1段階返信であり、返信を親にできないなど、単なる `if` からは分からない仕様を書く。
- **Like契約**：Likeが冪等であること、Unlikeが対象行の物理削除であること、集計とcurrent-user状態を一括取得する理由を書く。
- **性能・互換性**：GROUP BYやバッチ取得、Preload、特定のインデックス、外部仕様に合わせた変換など、素朴な実装を避ける理由を書く。測定結果がない性能断定は書かない。

### Layer別テンプレート

```go
// [対象]は、[コードだけでは分からない契約・制約]を守るために[処理]する。
```

```go
// [条件]の場合は、[影響範囲]を[理由]のために[処理]する。
```

```go
// [認証・所有者・公開境界]を[理由]から、[入力ではなく信頼できる値]を使う。
```

```go
// [操作A]と[操作B]を同じTransactionに入れ、片方だけ成功した状態を残さない。
```

日本語の説明コメントは、現在のThreadlyコードの文体に合わせて簡潔な文で書く。Swaggerの `@Summary` や `@Description` はOpenAPI契約のため、既存の英語形式を維持する。`//go:build`、`DO NOT EDIT`、MockGen・swagの生成ヘッダーは説明文ではなくツールの制御情報なので、書き換えない。

## レビュー時の問い

1. コメントを隠してコードを読んだとき、何が判断できないか。
2. コメントは、その行の実行時点の状態を説明しているか。
3. コメントの理由は、仕様・セキュリティ・整合性・性能・互換性のどれかに結び付いているか。
4. その情報はModel、Repository、Service、HTTP、UIのどの責務に属するか。
5. コード変更時にコメントが古くなったら、同じ差分で更新できるか。
6. コメントを足すより、名前・関数分割・型・テストで意図を表す方がよくないか。
