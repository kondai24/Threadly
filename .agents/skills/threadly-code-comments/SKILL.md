# Threadly Code Comments

## 基本原則

コードを読みやすくする責務は、まず命名・構造・関数分割で果たす。コメントは、コードの直訳ではなく、コードだけでは復元しにくい「実行時点の状態」「なぜその処理が必要か」「制約・影響範囲・契約」を短く伝えるために使う。

次の一文をコメントの合否判定に使う。

> そのコメントは、コメントが置かれた行を実行する時点の読み手に、コードからは得にくい情報を追加しているか。

## 適用手順

### 1. 実コードと契約を確認する

対象ブランチの実装、呼び出し元、テスト、API・DB設計を確認する。現在のコードにない処理や、過去の設計案を現行仕様としてコメントしない。Threadlyの開発タスクでは、対象プロジェクトのObsidian設計・Worklog・関連する `knowledge/Engineering/` と、現行コードを突き合わせる。

### 2. コメントの種類を判定する

次の優先順で判断する。

- **不要**：命名・型・構造を読めば分かる代入、条件、ループを逐語訳しない。
- **契約**：exportされたGo識別子、Swaggerアノテーション、ビルドタグ、生成コードのヘッダーなど、ツールや外部利用者が必要とする定型コメントを残す。
- **意図・制約**：セキュリティ、認可、データ整合性、互換性、性能、論理削除、トランザクション境界など、コードだけでは理由を推測しにくい場合に書く。
- **状態・時系列**：分岐や変換の直前・直後で、読み手が追っている状態を明示する必要がある場合に書く。まだ起きていない処理や、既に終わった処理を早すぎる・遅すぎる位置に書かない。

### 3. 実行地点の近くに書く

コメントを説明対象の直前、または対象ブロック内に置く。`if` の分岐ごとの状態はその分岐内に書き、分岐前の共通条件だけを `if` の前に書く。1つのコメントで複数の遠い処理を説明しない。

### 4. Threadlyの責務に合わせて書く

コメントの内容をレイヤーの責務に合わせる。

- **Domain Model**：値の不変条件、関連の意味、公開仕様に現れないデータ制約を書く。GORMタグの直訳は書かない。
- **Repository / GORM**：クエリの見た目からは分からない検索境界、ロック、トランザクション、`RowsAffected` の意味、ORMエラーの変換、関連データの削除範囲を書く。`Where` や `Delete` の直訳は書かない。
- **Service**：ビジネスルール、認証済みUserを使う理由、所有者境界、エラーを同じ応答へまとめる理由、複数Repositoryをまたぐ整合性を書く。
- **Controller / Route**：HTTP契約、Middleware順序、Swaggerとの対応など、HTTP層で必要な情報を書く。Serviceの処理を重複説明しない。
- **React / TypeScript**：React Queryのinvalidate、認証状態・リダイレクト、生成APIとの境界など、UIコードだけでは意図しにくい状態同期を書く。自明なイベントハンドラには書かない。
- **Test**：なぜ通常と異なるfixture、時刻、並行性、DB条件が必要なのかを書く。assertそのものの読み上げは書かない。

### 5. コメントを自己レビューする

次をすべて確認する。

- コードの直訳ではなく、新しい情報を含むか。
- コメントが置かれた時点の状態・条件と、説明内容が一致しているか。
- 「なぜ」「どの制約を守るか」「何に影響するか」の少なくとも1つが明確か。
- 現行の設計・テスト・API契約と矛盾しないか。
- 将来の変更で陳腐化しやすい実装詳細を避けているか。
- 命名変更や関数分割でコメント自体を不要にできないか。
- 秘密情報、個人Vaultのパス、内部文書の詳細を共有リポジトリのコメントへ持ち込んでいないか。

具体例、Threadlyの既存パターン、Go/React/Swagger別の書き分けは [references/comment-standards.md](references/comment-standards.md) を参照する。

## Threadlyでの検証

コメントだけの変更でも、対象言語の通常の検証を行う。Goは `gofmt -d` と対象テスト、APIアノテーションを変更した場合は `make -C api swag` の差分確認、Frontは対象に応じて `npm run lint` または `npm run build`、共通して `git diff --check` を使う。検証していないものは完了扱いにしない。

生成ファイルは手編集しない。`api/docs/`、`front/src/orval/`、MockGen出力の定型コメントは保持し、変更が必要なら生成元と生成コマンドを特定する。
